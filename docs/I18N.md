# Internationalisation

## Languages

English (`en`), Tamil (`ta`), Telugu (`te`), Kannada (`kn`) — **942 keys each,
complete**. Parity is enforced in CI by `npm run i18n:check`, which fails on a
missing key, an extra key, or a mismatched interpolation placeholder.

Tamil, Telugu and Kannada are not an afterthought here. They are the languages
the people using this product actually think in, and a screen that half-works in
Tamil is a screen that pushes a manager back to English and then to guessing.

## Rules

1. **No hard-coded user-visible English.** Every string comes from a locale
   resource. `eslint` and review catch the rest.
2. **A missing translation falls back to English — never to a raw key.** A
   screen showing `attendance.scanPrompt` is worse than one showing an English
   sentence.
3. **Enum values are translated at the edge, not stored translated.** The
   database holds `DISTANCE_VARIANCE`; the UI renders
   `t('anomalies.kinds.DISTANCE_VARIANCE')`. Storing a translated string would
   make the data untranslatable afterwards.
4. **Notifications and anomalies carry keys plus parameters, never sentences.**
   `title_key`, `body_key` and a `payload` of interpolation values, so a
   notification written while the manager used English reads correctly after
   they switch to Kannada — and so a future SMS channel can render in the
   _recipient's_ language rather than the sender's.
5. **Numbers, dates and units go through `src/lib/format.ts`**, which uses
   `Intl` with the active locale. Never string concatenation.
6. **Exported data is not translated.** CSV _headers_ are; the values are not. A
   registration number and a driver's name mean the same thing in every
   language, and translating them breaks matching the file against anything
   else.

## How it is wired

- `src/i18n/index.ts` — react-i18next, one namespace per locale, **dynamically
  imported per language**, so a Tamil user never downloads the Kannada bundle.
  Initialised before React mounts, so there is no flash of English.
- `src/i18n/languages.ts` — `resolveInitialLocale()` resolves
  **profile preference → device preference → browser language → English**.
- `src/i18n/fonts.ts` — the Indic script subsets are lazy-loaded per language
  from self-hosted `@fontsource` packages. Self-hosted rather than from Google
  Fonts: a depot connection should not depend on a third-party CDN, and the
  request is one fewer thing to leak.
- `<html lang>` is updated on every change, so screen readers switch voice and
  the browser hyphenates correctly.

## Adding a language

1. `cp -r src/i18n/locales/en src/i18n/locales/<code>` and translate.
2. Add the entry to `SUPPORTED_LOCALES` in `src/i18n/languages.ts`.
3. Add the value to the `app_locale` enum via a new migration.
4. If the script needs one, add its `@fontsource` subset in `src/i18n/fonts.ts`.
5. `npm run i18n:check` until it passes.

The check reports keys present in English and missing elsewhere, keys that exist
only in a translation, and any placeholder mismatch — `{{count}}` present in
English but absent in the translation is a runtime hole, not a style issue.

## Pluralisation

i18next plural suffixes (`_one`, `_other`) are used throughout, not manual
`count === 1` branches. Tamil, Telugu and Kannada have plural behaviours that a
hand-written branch gets wrong.

## Vocabulary

A constraint that survives translation, and the reason it is written down here
as well as in [SECURITY.md](SECURITY.md):

**No locale contains a word for fraud, theft, stealing or cheating.** The
vocabulary is "anomaly", "requires review", "distance mismatch", "unusual",
"needs a look". A translator adding a language inherits this rule; a translation
that sharpens the tone changes what the product _is_, not just how it reads.

The `npm run i18n:check` output also flags strings identical to English, which
is usually a translation that was never done — currently one per locale, and
they are genuine (a product name).

## Testing

`tests/unit/i18n.test.ts` asserts key parity, placeholder parity, that no value
is an empty string, and that the fallback chain resolves to English rather than
to a key. `tests/e2e/i18n.spec.ts` switches language in a real browser, asserts
the rendered script by Unicode range, reloads to confirm the preference is
persisted on the profile, and sweeps every main screen for anything that looks
like a leaked translation key.
